# Harlan's Legacy — Production Deployment (Vercel + Supabase)

This turns the local, file-based CMS into a persistent production system **without
changing the public website, the URLs, the admin UI, or the domain**.

```
harlanslegacy.com  →  Vercel
                        ├─ public static site      (generated by build.js)
                        ├─ /admin/                  (unchanged CMS UI)
                        └─ /api/*                    (serverless functions)
                                   │
                                   ▼
                               Supabase
                        ├─ Postgres (JSONB)  — stories, site, entities, photos
                        └─ Storage           — photo / editorial originals
```

Local development is **unchanged**: with no environment variables set, `node
server.js` and `npm run build` use the local `data/*.json` files exactly as before.

---

## What changed in the codebase (for reference)

| File | Purpose |
|---|---|
| `lib/store.js` | Data layer. **File backend** locally; **Supabase backend** when `SUPABASE_URL` + `SUPABASE_SERVICE_ROLE_KEY` are set. |
| `lib/records.js` | Shared story record logic (used by local server **and** serverless — one copy). |
| `api/[...path].js` | Vercel serverless function: the whole admin API, backed by Supabase. |
| `lib/hydrate.js` | Build step: pulls Supabase → local `data/*.json` + downloads photo originals. No-op locally. |
| `lib/collect-public.js` | Build step: assembles the deployable `public/` dir (excludes `data/`, `lib/`, source). |
| `supabase/schema.sql` | The database schema (JSONB) + Storage buckets. |
| `lib/migrate.js` | One-time: pushes existing JSON + photo originals into Supabase. |
| `vercel.json` | Build command, output dir, function config. |
| `server.js`, `build.js` | Unchanged behaviour locally; refactored to share `records.js` / expose `deriveData`. |

## 1) Supabase setup

1. Create a project at <https://supabase.com> (any region near you).
2. **SQL:** Dashboard → **SQL Editor** → **New query** → paste the entire contents of
   `supabase/schema.sql` → **Run**. This creates:
   - table **`documents`** `(key text pk, data jsonb, updated_at)` — holds `site`, `entities`, `photos`, `story_photos`.
   - table **`stories`** `(id int pk, data jsonb, updated_at)` — one row per memory.
   - Storage buckets **`photos`** and **`story-photos`** (public read).
   - Row Level Security is **enabled with no policies**, so only the server-side
     service-role key can read/write — the browser never can.
3. **Get your keys:** Dashboard → **Project Settings → API**:
   - **Project URL** → `SUPABASE_URL`
   - **`service_role` secret** → `SUPABASE_SERVICE_ROLE_KEY` (⚠️ secret — server only).

### Tables / buckets required
- Tables: `public.documents`, `public.stories` (created by the SQL above).
- Buckets: `photos`, `story-photos` (created by the SQL above; public).

## 2) Migrate existing data into Supabase (run once, locally)

```bash
npm install
SUPABASE_URL="https://YOUR-REF.supabase.co" \
SUPABASE_SERVICE_ROLE_KEY="YOUR-SERVICE-ROLE-KEY" \
npm run migrate
```
(Windows PowerShell:)
```powershell
$env:SUPABASE_URL="https://YOUR-REF.supabase.co"
$env:SUPABASE_SERVICE_ROLE_KEY="YOUR-SERVICE-ROLE-KEY"
npm run migrate
```
This upserts `data/site.json`, `entities.json`, `photos.json`, `story-photos.json`,
all 11 stories, and uploads every photo original to Storage. It is **idempotent**
(safe to re-run) and never deletes your local files.

Verify in Supabase → **Table Editor**: `stories` has your rows; `documents` has
`site` / `entities` / `photos` / `story_photos`. Storage → `photos` has the originals.

## 3) Vercel environment variables

Vercel → your Project → **Settings → Environment Variables** (Production, and
Preview if you use it):

| Name | Value |
|---|---|
| `SUPABASE_URL` | `https://YOUR-REF.supabase.co` |
| `SUPABASE_SERVICE_ROLE_KEY` | your service-role secret |
| `ADMIN_TOKEN` | any long random string (the admin password) |
| `VERCEL_DEPLOY_HOOK_URL` | created in step 4 |

## 4) Vercel settings

1. **Deploy Hook:** Settings → **Git → Deploy Hooks** → create one (name `publish`,
   branch `main`). Copy its URL into the `VERCEL_DEPLOY_HOOK_URL` env var (step 3).
2. **Build & Output** (usually auto-detected from `vercel.json`):
   - Build Command: `npm run build:vercel`
   - Output Directory: `public`
   - Install Command: `npm install` (default)
3. Framework Preset: **Other** (this is a custom static build).
4. Domain: `harlanslegacy.com` stays attached to this project — **do not change it**.

`vercel.json` already sets the build command, output dir, and the
`api/[...path].js` function (30s / 1024 MB). No further config needed.

---

## 5) Deploy

- Push the repo to the Git remote connected to Vercel (or `vercel --prod` with the CLI).
- Vercel runs `npm run build:vercel`:
  `hydrate` (pull Supabase → local) → `photos` (regenerate derivatives) →
  `build.js` (generate the static site) → `collect-public` (assemble `public/`).
- The public site + `/admin/` + `/api/*` deploy together. URLs are unchanged
  (`/story/…`, `/family/…`, `/journey/…`, `/place/…`, `/object/…`, `/event/…`).

**Publish flow:** admin saves → Supabase → the API calls the Deploy Hook → Vercel
rebuilds from Supabase → the updated public site goes live (typically ~1 min).

## 6) Testing checklist

**Production admin** (`https://harlanslegacy.com/admin/`)
- [ ] It prompts for the admin token; a wrong token shows a clear **Unauthorized** message (not "0 memories").
- [ ] With the correct token it lists **all memories** (loaded from Supabase).
- [ ] If the API/Supabase is unreachable, a clear error + **Retry** appears (never a silent 0).

**CRUD → persistence**
- [ ] Create a memory → save → it appears in the list, and in Supabase `stories`.
- [ ] Reload the page → the memory is still there (persistent).
- [ ] Edit + Publish → after the rebuild finishes, it appears on the public site,
      in the Archive, its category/journey, and search.
- [ ] Delete → gone from list, Supabase, and (after rebuild) the public site.
- [ ] `published` / `coming-soon` / `draft` states behave as before.

**Photos**
- [ ] Upload a family photo / story image → stored in Supabase Storage.
- [ ] After the rebuild, the responsive derivatives appear on the site.
- [ ] Family galleries and per-story editorial images stay separate.

**Public site**
- [ ] All existing URLs load; design/typography/animations/responsive unchanged.
- [ ] `harlanslegacy.com` serves from Vercel on the existing domain.

**Local dev (must still work)**
- [ ] With no env vars: `node server.js` → admin lists 11 memories; `npm run build` generates the site — all from local JSON, exactly as before.

## Security notes

- The **service-role key is never sent to the browser** — it lives only in Vercel
  env vars and is used inside `api/[...path].js` / `lib/store.js` (server-side).
- The admin API is gated by `ADMIN_TOKEN` (sent as `x-admin-token`). The `/admin/`
  page is static and public, but it cannot read or change anything without the token.
- RLS is enabled on both tables with no anon policies, so a leaked anon key grants
  nothing.
- **Recommended upgrade path (optional):** replace the shared token with Supabase
  Auth (email magic-link) + a `is_admin` check in the serverless function, or put
  Vercel's built-in password protection in front of `/admin`. The token gate is a
  solid, simple production baseline; both upgrades slot in without touching the UI.

## Honest limitations

- Uploaded photo **derivatives** are regenerated at build time (not per request),
  so a newly uploaded image shows its Storage original in the admin immediately and
  its optimized responsive versions after the next rebuild completes.
- The rebuild is asynchronous (Deploy Hook) — the public site updates within ~1
  minute of publishing, not instantly.
